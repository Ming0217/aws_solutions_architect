PhotoShare — Phase 2

A resilient 3-tier web app with a serverless image-processing pipeline, built as reproducible infrastructure-as-code.

Region us-east-1  ·  CloudFormation IaC  ·  deployed & validated end-to-end, then torn down

Walkthrough

What we'll cover

PhotoShare separates a public web tier from private data, and offloads image processing to a serverless pipeline. Three views, in sequence:

01

Main architecture

The request path, the Multi-AZ data tier, and the three layers of data isolation.

02

Async image pipeline

How an upload is processed in the background without the web request waiting.

03

Build & operations

How the app image is built and shipped, and how the fleet is administered and observed.

01 — Main architecture

Request path & data tier

  • Only the ALB is internet-facing; everything else is private.
  • Web tier is an ASG across 2 AZs in private subnets, behind the ALB.
  • RDS MySQL is private and Multi-AZ (synchronous standby).
  • EC2 reads the DB password from Secrets Manager (decrypted by KMS) — no hardcoded creds.
  • Outbound egress goes through a single NAT Gateway.

01 — Main architecture

Three independent layers to the data

  • 1No route to the internet — RDS sits in a private subnet with no IGW route.
  • 2RDS "Public Access" off — a separate switch from subnet routing.
  • 3Security group sources the web SG (not a CIDR) — only the web tier can reach port 3306, even inside the VPC.
  • No static credentials — Secrets Manager + KMS; IAM roles, never keys in code.
  • S3 Block Public Access — photos are served through the app, never from the bucket.
  • Admin via Session Manager — zero inbound ports, no SSH.

Only after all three network checks pass does a connection even reach MySQL authentication.

01 — Main architecture

Reliability & scaling

  • Web: ASG across 2 AZs behind the ALB — self-healing (watched it replace an unhealthy instance live).
  • Data: RDS Multi-AZ synchronous standby in the second AZ.
  • Scaling: ASG target-tracking on CPU; image bursts absorbed by serverless Lambda.
  • Accepted SPOF: a single NAT Gateway (outbound only) — a deliberate cost tradeoff.

02 — Async image pipeline

Processing an upload in the background

  • A new photo in S3 fires an ObjectCreated event.
  • Lambda (outside the VPC) processes the image metadata.
  • It calls back through the ALB's public DNS, so the web app writes to RDS — Lambda never touches the DB directly.
  • That keeps Lambda's IAM role minimal (S3 + outbound HTTP).
  • Repeated failures land in an SQS DLQ instead of looping.

03 — Build & operations

How it's built and run

  • App image built in the cloud: CodeBuild → ECR (no local Docker).
  • Instances pull the image from ECR on launch.
  • Admin via Session Manager — no SSH, no open ports.
  • CloudWatch collects logs, metrics, and alarms from EC2 and Lambda.

Wrap-up

Well-Architected & cost

Security

Private DB, three isolation layers, no static credentials, S3 locked down.

Reliability

ASG across 2 AZs + RDS Multi-AZ + DLQ; self-healing verified live.

Performance

ASG target-tracking; serverless image processing scales with bursts.

Cost

t3.micro + single NAT; pay-per-use Lambda/S3. ~$0.14/hr all-in (~$4 for a demo day).

Operational excellence

Reproducible CloudFormation; image built via CodeBuild; one-command teardown.

Takeaway

A live deploy surfaced real bugs static checks missed — the point of validating on real AWS.
